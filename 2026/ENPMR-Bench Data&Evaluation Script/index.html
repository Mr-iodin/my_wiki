    ENPMR-Bench Data&Evaluation Script

    🔗 Github：https://github.com/xingqwq/ENPMR-Bench?utm_source=chatgpt.com

    这套数据专门研究一个问题：

    ​ 当用户在当前对话中表达某种情绪困境或隐性情感需求时，大模型应该从用户的长期个人记忆中主动召回哪些内容，才能更好地提供情感支持？

    它的基本组织方式是：

    ​ 用户画像（Persona）→ 长期记忆库（Memory Bank）→ 当前对话（Dialogue）→ 目标记忆（Golden Memory）

    可以把它理解成一个模拟长期记忆检索任务的实验环境：

    1. 系统先拥有一个用户的个人画像。
    2. 用户长期积累了大量个人记忆。
    3. 用户在某个新的情境下与 AI 交谈。
    4. 系统需要判断当前对话隐含的情感需求。
    5. 从长期记忆中找到对当前情境真正有帮助的记忆。

    [!NOTE]

    ​ ⚠️ 注意：这里的目标不只是找到语义上最相似的记忆，而是找到对当前情感支持有价值的记忆。

    这是 ENPMR-Bench 的核心设计之一。

    当前潜在情感需求 论文指定的记忆类别 可能发挥的支持作用
    生理需求（Physiological） preference 根据用户习惯给予适当建议
    爱与归属（Love and Belonging） relationship 提醒用户已有的人际支持
    尊重需求（Esteem） highlight、relationship 帮助用户获得认可与信心
    自我实现（Self-actualization） goal、power、highlight 联系用户的目标、优势及成就

    例如，用户说：

    ​ “我最近感觉自己特别没用，好像什么事情都做不好。”

    ​ 系统推断其可能存在尊重需求（Esteem Need），因此可能优先召回 highlight 中“过去成功完成项目”的记忆。

    1.2 JSON 文件的内部结构

    数据集结构：

    persona（人物）
   ├── personas：7个中文画像 + persona + preference + id
   ├── 结构化记忆：big_event / relationship / power / goal / highlight
   └── 评测三件套：
                 dialog ← 考题（2,692）
                 memory_bank ← 候选记忆池（11,846）
                 memory_bank_to_id ← 索引

    以 林夏 为例，

    整个文件：人物列表
└── 一个人物，例如 personas[0] = 林夏
    ├── ① 人物画像：她是谁、平时怎样生活
    ├── ② 分类资料：她的朋友、能力、目标、重要经历
    ├── ③ dialog：用这些记忆编出的情感支持测试题
    ├── ④ memory_bank：把过往信息整理成可检索的记忆
    └── ⑤ memory_bank_to_id：帮助定位记忆的索引表
    1.2.1 顶层结构

    每个 Persona 是一个独立的用户对象，主要包含以下字段：

    字段 作用 研究价值
    id 用户编号 区分用户
    persona 英文用户画像摘要 用户背景建模
    基本信息 年龄、职业、学历等 用户属性
    人格特质 性格特征 个性化支持
    日常习惯与作息 生活习惯 行为偏好
    社交关系 社会关系概况 社会支持建模
    情绪模式 情绪反应与调节方式 情绪相关分析
    个人目标 长期发展目标 目标导向检索
    沟通风格 表达与交流特点 个性化生成
    preference 用户具体偏好 偏好记忆检索
    big_event 人生重要主题 记忆组织与关联
    relationship 人际关系记忆 社会支持记忆
    power 能力与技能记忆 能力支持记忆
    goal 目标记忆 目标支持记忆
    highlight 重要经历与成就 成功经验召回
    dialog 情感支持对话样本 检索测试集
    memory_bank 长期记忆候选库 检索语料库
    memory_bank_to_id 记忆名称与记忆编号映射 Gold Memory 定位

    这些字段不是彼此独立的。例如，一个用户的某个重要人生主题下面，可以同时存在人际关系、技能、目标和重要经历等不同类型的记忆。

    1.2.2 big_event：人生主题与记忆组织框架

    这是整个数据集非常重要的一个结构，因为它提供了一个初步的长期记忆组织结构。它不是普通的事件记录，而是将用户的人生经历划分成若干个较大的主题。

    传统向量检索通常只关心：

    当前对话与哪条记忆的语义相似度最高？

    但是有了 big_event，我们还可以研究：

    当前困境与用户过去哪个人生主题有关？是否应该优先检索该主题下的记忆？

    例如：用户因为国际客户拒绝合作而产生职业焦虑。

    ​ 系统可以先识别当前困境与「自由职业转型」「个人品牌建设」等主题有关，再在相应主题中寻找具体记忆。

    这就为主题约束检索、分层检索和候选记忆筛选提供了基础。

    以第一个 Persona——林夏为例：

    编号 人生主题
    0 自由职业转型
    1 健康生活方式养成
    2 国际设计项目合作
    3 插画作品集创作
    4 素食烹饪与美食创新
    5 城市自然探寻与徒步
    6 个人品牌建设
    7 环保与可持续创作
    8 深度社交与行业交流
    9 心灵成长与情绪调节
    10 环球旅行与自然体验
    11 独立工作室筹备

    big_event 在其他字段中经常不是直接存储主题名称，而是存储数字字符串，例如 "0"、"1"、"2"。

    例如：

    big_event = "0"

    就表示这个记忆属于该 Persona 的第一个人生主题：自由职业转型。

    可通过下面的方式获取具体主题：

    theme_id = int(memory["big_event"])
theme = persona["big_event"][theme_id]
    1.2.3 五种核心记忆类型

    README 明确将记忆分为五种长期记忆结构：

    这里有一个很重要的区别：

    • big_event 是较大的生活主题。
    • highlight 是这个主题下具体的重要经历。
    • goal 是用户想要实现的目标。
    • power 是用户拥有的能力。
    • relationship 是与用户相关的人际支持。
    • preference 是用户稳定的个人偏好。

    例如：

    ​ 这五种记忆类型并不是五种情绪，而是五种不同的个人记忆内容。

    ​ 这一点在后续设计情感需求驱动检索时尤其重要：系统不能简单地认为焦虑就检索 highlight，孤独就检索 relationship，而应该根据当前需求判断哪类记忆、哪条具体记忆真正有帮助。

    1.2.4 memory_bank：真正进行检索的候选记忆库

    如果说前面五种记忆是结构化的原始资料，那么 memory_bank 就是将这些记忆整理成统一格式之后形成的候选记忆集合。

    每条记忆通常包含：

    字段 解释
    date 记忆产生或记录日期
    type 记忆类型
    big_event 所属人生主题编号
    event 记忆文本
    dialog 形成该记忆的历史对话
    label 部分重要经历的标签

    这里有一个非常关键的设计：

    每条记忆不仅有一段摘要，还保留了与其形成有关的历史对话。

    例如，林夏的某条记忆：

    type: relationship

event:
陈颖，老友，关系好，职业为环境保护志愿者。
温和细致，热衷环保公益，精通素食料理。
经常带林夏探索新素食餐厅，
并参与社区环保艺术装置制作。

dialog:
用户和AI过去围绕陈颖进行的历史交流。

    这意味着你可以研究两种不同的检索表示：

    • Summary-based Retrieval： 只使用 event 作为记忆文本。
    • History-enhanced Retrieval： 使用 event + dialog 作为记忆文本。

    两者可以做消融实验，研究历史对话是否能提高记忆检索效果。

    ⚠️ 要注意：历史对话是记忆形成时的对话，不是当前情感支持对话，不能将两者混淆。

    1.2.5 memory_bank_to_id：记忆编号映射

    它的作用是：将记忆名称映射到 memory_bank 中对应的下标。

    例如：

    {
  "陈颖": 0,
  "刘晨": 1,
  "线上艺术沙龙主持与互动引导": 2,
  "何嘉明": 3
}

    假设：

    memory_id = persona["memory_bank_to_id"]["陈颖"]

    得到：

    memory_id = 0

    那么：

    memory = persona["memory_bank"][memory_id]

    就可以找到陈颖对应的完整记忆。

    它实际上解决了两个问题：

    1. 找到当前对话应该召回的正确记忆。
    2. 将自然语言形式的 Gold Memory 转换成可用于计算指标的数字 ID。

    对原始数据完整 JSON 做了映射检查：

    • 总记忆条目：11,846。
    • 有映射编号的条目：11,729。
    • 有117条记忆没有出现在映射表中。
    • 但2,692条对话的目标记忆均能通过映射表找到。

    因此，进行实验时可以使用 memory_bank_to_id 定位 Gold Memory，但不要直接假设每一条候选记忆都有对应映射。

    另外，映射是每个 Persona 内部独立的，不能把不同用户的 memory ID 当作全局唯一编号。

    1.3 数据集到底有多少种记忆？分布如何？

    进一步对完整 JSON 做了统计，这里需要区分两个概念：

    • memory_bank：所有可供检索的候选记忆。
    • dialog：对话中指定的目标记忆类别。

    两者数量并不相同。

    1.3.1 候选记忆库分布

    基于完整 JSON 的实际统计。

    记忆类别 数量 占比
    highlight 3,729 31.48%
    power 3,463 29.23%
    relationship 2,324 19.62%
    goal 1,719 14.51%
    preference 611 5.16%
    总计 11,846 100%

    可以看到，highlight 和 power 占比最高。

    这说明该数据集并不是以日常偏好记忆为主，而是包含大量能力、成就、经历和人际关系记忆。

    这对于研究成功经历召回、能力支持型检索以及关系支持型检索非常有价值。

    1.3.2 对话目标记忆分布

    再来看2,692条对话中的 Gold Memory 类型：

    目标记忆类型 对话数量 占比
    preference 400 14.86%
    relationship 573 21.29%
    power 573 21.29%
    goal 573 21.29%
    highlight 573 21.29%

    这里有一个明显特点：

    除了 preference 以外，其余四类目标记忆数量完全相同。

    因此，原始对话任务在四种主要记忆类别之间具有较好的数量平衡。

    但候选记忆库本身并不平衡，所以实验时不能只看目标类别分布，还需要考虑不同记忆类型的候选数量差异。

    1.4、dialog：数据集真正要评测的任务

    如果说 memory_bank 是检索库，那么 dialog 就是检索任务的测试样本。

    每条对话有七个字段：

    字段 具体含义
    Scene 当前情感困境的场景描述
    Dialogue 用户与 AI 的实际对话
    Memory Turn AI 首次召回目标记忆的位置
    prompt 生成这条对话时使用的完整提示词
    big_event 对应的人生主题
    type 目标记忆的类型
    memory 标准答案，即 Gold Memory

    其中，最重要的是 Memory Turn、type 和 memory。

    1.4.1 用一个真实数据样本理解检索任务

    我们继续使用林夏这个 Persona。

    假设当前发生了这样的事情：

    这个样本体现了一个非常重要的检索逻辑。用户当前表达的是：

    • 自我怀疑；
    • 害怕受到批评；
    • 担心能力不足；
    • 渴望得到认可。

    系统最终没有简单地召回一条与「设计」语义相似的记忆，而是召回了一个曾经给予她支持和认可的合作伙伴。

    为什么这条记忆有价值？

    因为它能为当前困境提供真实的社会支持证据。

    如果只使用普通向量检索，可能会找到其他设计项目、设计技能或者作品集相关记忆，但不一定能找到真正具有支持价值的人际关系记忆。

    这正是 ENPMR-Bench 想要考察的能力。
